# TDD: цикл Red-Green-Refactor

## Введение

Разработка через тестирование (Test-Driven Development, TDD) - подход придуманный Кентом Беком в книге "Экстремальное программирование: разработка через тестирование". Заключается он в том, что перед написанием какой-то функции или изменением уже имеющейся мы сначала делаем тест под эту логику, затем изменяем код чтобы он проходил этот тест и только затем, после того, как прошли тест - рефакторим код. Работа идёт короткими циклами Red-Green-Refactor.

## Этапы цикла

**Red.** Пишем тест для новой функции или фичи и запускаем его. Самое главное чтобы код этот тест не проходил - тест горел красным.

**Green.** Меняем функцию чтобы тест заработал, и снова запускаем все тесты. На этом этапе мы даже можем не задумываться о стиле кода, нам нужно просто пройти тест.

**Refactor.** Когда тесты прошли, приводим код в порядок. После рефактора запускаем тесты ещё раз, чтобы убедиться, что программа ведёт себя корректно и тесты проходятся. Для следующей фичи начинаем цикл заново.

## Пример расчёта стоимости доставки

Рассмотрим пример с доставкой у магазина. У нас есть какая-то функция, которая считает стоимость доставки товара. Сейчас она всегда возвращает 300 рублей. То есть любая доставка стоит 300 рублей. Мы же хотим сделать так, чтобы при заказе от 1500 рублей доставка была бесплатной. Функция принимает неотрицательную сумму заказа в целых рублях и возвращает стоимость доставки в рублях.

Исходная функция:

```python
def shipping_cost(total: int) -> int:
    return 300
```

### Red

Предполагаем, что один тест на сумму 1499 рублей был - ожидаем 300. Этот тест проверяет исходную логику функции, до изменения. Сделаем тест для проверки нового функционала - при заказе 1500 рублей - ожидаем 0 рублей за доставку. Напишем простые тесты на pytest.

Тесты

```python
from shipping import shipping_cost


def test_paid_below_threshold():
    assert shipping_cost(1499) == 300


def test_free_at_threshold():
    assert shipping_cost(1500) == 0
```

Ожидаемо, наш код проходит первый тест, но на втором ловит красный - первый этап цикла TDD выполнен.

### Green

Добавим в функцию одно условие. Если сумма заказа больше или равна 1500 рублей, функция вернёт ноль. Для меньших сумм действует тариф 300 рублей. Запускаем тесты заново - оба пройдены. Второй этап цикла TDD пройден.

```python
def shipping_cost(total: int) -> int:
    if total >= 1500:
        return 0
    return 300
```

### Refactor

Теперь выполняем третий этап цикла TDD - рефактор. Это этап где уже можно применить максимум креативности. Введём отдельные константы на стандартную цену доставки и порог после которого доставка становится бесплатной. Поправли, запускаем тесты - снова всё зелёное. Цикл завершён - функция работает, протестирована и отрефакторена.

```python
FREE_SHIPPING_FROM = 1500
STANDARD_SHIPPING_COST = 300


def shipping_cost(total: int) -> int:
    if total >= FREE_SHIPPING_FROM:
        return 0
    return STANDARD_SHIPPING_COST
```

## Пример из книги Кента Бека

Тесты могут показаться до боли простыми. Зачем вообще писать тест для функции с одним `if`? В TDD новое правило сначала записывают в виде теста, даже если для реализации достаточно одного условия.
В предисловии своей книги Кент Бек формулирует правило словами "Пишите новый код, только если у вас уже есть падающий автоматический тест".

## TDD в работе с ИИ-агентами

В документации Claude Code есть пример задания на исправление ошибки входа после истечения сессии. Сначала агент пишет падающий тест, который воспроизводит сбой (Red). Затем правит код и запускает тест снова (Green). Если проверка всё ещё падает, агент читает отчёт и делает следующую правку. Тест заранее задаёт критерий готовности, поэтому агент может проверять каждую попытку самостоятельно.
Плюсы:

-   Точная цель до написания кода. Тест фиксирует ожидаемый результат, чтобы агенту было понятно, какое поведение нужно реализовать.
-   Меньше ручных подсказок. Агент сам запускает pytest, видит, какой сценарий упал и чем результат отличается от ожидаемого, и может сразу сделать следующую правку.
-   Быстрая проверка регрессий. Вместе с новым тестом агент запускает старые и может заметить, что правка сломала уже работавший сценарий.

## Заключение

Тест, с которого начался цикл, пригодится и после того, как функция заработает. Мы запускаем его вместе с остальными тестами при рефакторинге и при добавлении новых правил. Если очередная правка заденет уже работающий сценарий, тест покажет, где результат разошёлся с ожиданием.

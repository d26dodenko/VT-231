# Бизнес-правила

| № | Бизнес-правило | Реализация в коде | Тестовые границы |
|----------|-----|---------------------|--------------------------------------------------------------------------------------------------|
| BR1 | Если minutes < 0 — ValueError | if minutes < 0: raise ValueError | −1 / 0                                                         |
| BR2 | Если distance_km < 0 — ValueError | if distance_km < 0: raise ValueError | −1 / 0                                                 |
| BR3 | Если minutes == 0 — поездка не состоялась, стоимость равна 0 | ветка if minutes == 0: base = 0.0 | 0 / 1                          |
| BR4 | При 0 < minutes ≤ 30 действует базовый тариф — 100 | ветка elif minutes <= 60 | 1 / 30                                            |
| BR5 | При 30 < minutes ≤ 60 — 100 + (minutes − 30) * 5 | ветка elif minutes <= 60 | 31 / 60                                             |
| BR6 | При minutes > 60 — 250 + (minutes − 60) * 8 | ветка else | 61                                                                     |
| BR7 | За каждый км свыше 10 добавляется 20 (доплата за износ) | if distance_km > 10: base += (distance_km − 10) * 20 | 10 / 10.01 / 15  |

В модуле rental.py выделил 8 бизнес-правил, которые делятся на три группы:
1. ограничения (BR1, BR2) — валидация входных данных;
2. вычисления (BR3–BR7) — тарифная сетка и доплата;
3. модификаторы условий (BR8) — скидка студента.

# Задание 2:
## Входные параметры:
Функция calculate_rental_cost(minutes: int, distance_km: float, is_student: bool) -> float принимает три входных параметра:

•	minutes – int – длительность поездки в минутах – определяет базовый тариф (BR3–BR6)

•	distance_km – float – пройденное расстояние в километрах – определяет доплату за износ (BR7)

•	is_student – bool – студенческая скидка – модификатор итоговой суммы (BR8)

## Выходной параметр:
•	возвращаемое значение – float – Итоговая стоимость аренды электросамоката
## Допустимые значения и недопустимые значения:
## minutes (int)
- Допустимые: 0 → стоимость 0 (поездки не было)
- Допустимые: 1 … 30 → базовый тариф 100
- Допустимые: 31 … 60 → 100 + (m−30)·5
- Допустимые: > 60 → 250 + (m−60)·8
- Недопустимые: < 0 (−1, −100…) → ValueError
## distance_km (float)
- Допустимые: 0 … 10 → без доплаты за расстояние
- Допустимые: > 10 → + (km−10)·20 за каждый км сверх 10
- Недопустимые: < 0 (−0.5, −1…) → ValueError
## is_student (bool)
- Допустимые: False → скидка не применяется
- Допустимые: True → итог умножается на 0.7

## Классы эквивалентности

| Класс | Условие (обычный режим) | Результат                    |
|-------|-------------------------|------------------------------|
| 1 | minutes < 0                 |    ValueError                |
| 2 | distance_km < 0             | ValueError                   |
| 3 | minutes == 0                | 0.0                          |
| 4 | minutes in [1; 30]          | 100.0                        |
| 5 | minutes in (30; 60]         | 100 + (minutes − 30)·5       |
| 6 | minutes > 60                | 250 + (minutes − 60)·8       |
| 7 | distance_km in [0; 10]      | без доплаты                  |
| 8 | distance_km > 10            | base + (distance_km − 10)·20 |
| 9 | is_student == False	       | без скидки                   |
| 10 | is_student == True         | base × 0.7                   |
## Граничные значения:
Границы определяются точками переключения логики — там, где меняется формула (<, <=, >).


| Граница                 | Значение «до» | Значение «на» | Значение «после»            | Что меняется                   |
|-----------------------  |---------------|---------------|-----------------------------|--------------------------------|
| Начало допустимого      | —             | 0             | 1                           |0 (не было) → базовый тариф 100 | 
| Конец базового тарифа   | 29            | 30            | 31                          | 100 → переменная формула       | 
| Конец второго тарифа    | 59            | 60            | 61                          | 100+(m−30)·5 → 250+(m−60)·8    | 

Проверяем: 0 / 30 / 31 / 60 / 61 (плюс «чуть меньше/больше» — 29, 59).
## По расстоянию (distance_km):

| Граница                 | Значение «до» | Значение «на» | Значение «после»            | Что меняется                   |
|-----------------------  |---------------|---------------|-----------------------------|--------------------------------|
| Порог доплаты           | 9.99          | 10            | 10.01                       |без доплаты → +(km−10)·20       |

## По скидке (is_student):
| Граница             | False      | True |  Что меняется  |
|-------------------- |------------|------|--------------- |
| Переключение скидки | без скидки | ×0.7 | итоговая сумма |

## Оставшиеся риски:

1). Нечисловые входы (None, строки): возникнет TypeError, а не ожидаемый ValueError. Причина - валидация проверяет только < 0.

2). Не-bool для is_student (1, 0, "yes"): тихий проход в ветку скидки (в Python bool — подкласс int). Причина - нет проверки типа.

3). Дробное расстояние у порога (10.001 км): погрешность float при > 10. Причина - арифметика чисел с плавающей точкой.

4). Очень большие значения minutes/distance_km: нереалистичные суммы, потеря точности, переполнение тарифной логики. Причина - нет верхнего предела валидации.

5). Изменение бизнес-правил (новые тарифы): тесты устареют, если правила поменяются, а тесты — нет. Причина - тесты жёстко фиксируют текущие числа.

Таким образом, не обеспечены устойчивость к некорректным типам данных и защита от «мусорных» входов.

## Тестирование важно для качества, так как:

1. Раннее обнаружение дефектов. Правило «1:10:100» показывает, что ошибка, найденная на этапе тестирования модуля, обходится в разы дешевле, чем обнаруженная в продакшене.
2. Регрессионная защита. Набор из 15 автотестов фиксирует текущее поведение. Любое изменение тарифов, порогов или скидок мгновенно покажет, отклонилось ли поведение от бизнес-правил.
3. «Живая спецификация». Каждый тест документирует своё бизнес-правило: глядя на test_second_tariff_start, сразу понятно, что 31 минута должна стоить 105.
4. Объективная метрика. Покрытие 100% — подтверждение того, что ни одна строка не осталась непроверенной.
5. Место в жизненном цикле (Shift Left). Тесты писались вместе с кодом, на стадии разработки, а не после релиза. Это снижает стоимость и повышает качество.
